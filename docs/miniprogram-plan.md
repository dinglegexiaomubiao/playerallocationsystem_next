# 微信小程序化规划 · 深圳LaRoja Dota2社区

> 结论：**可行**。后端几乎不用改（43 个 API 全部复用），页面层需重写（23.4k 行前端代码无法直接搬），
> 企业主体 + ICP 备案即可满足「社交 > 社区/论坛」类目要求。
> 原生小程序 + 与网站功能对齐，预计 **6~7 周开发**，备案审核 **2~4 周**（可与开发并行）。

---

## 一、先说清楚「值不值得做」

网站现在已有完整响应式（560/720/820/900/920px 五档断点），手机浏览器能正常用。
小程序的增量价值只有四条，如果这四条都用不上，做的意义不大：

| 价值 | 说明 | 对本站的实际意义 |
|---|---|---|
| **微信内直达** | 群里发链接直接点开，不用记域名、不用跳浏览器 | 群友最高频的访问路径 |
| **分享卡片** | 分享出去的卡片带标题/封面，不是裸链接 | 赛事开赛、成绩公布时拉人效果好 |
| **订阅消息** | 开赛/报名截止/比赛结果主动推送 | **这是网站做不到的**，也是最有价值的一条 |
| **免登录浏览** | 不用注册就能看赛程和成员 | 降低群友的打开成本 |

反过来，代价是：
- 两套前端并行维护（改接口要同时验证两端）
- 审核周期与合规成本
- 小程序无法做后台管理，`/admin` 那 4659 行永久留在网页端

**判断**：如果目标是「让群友在微信里更快看到赛程和自己的战绩 + 开赛提醒」，值得做。
如果只是「把网站搬到小程序里」，收益不足以覆盖维护成本。

## 二、可行性核查（已实测，不是推测）

### 1. 接口层：43 个 API 可直接复用

小程序 `wx.request` 不是浏览器，**不存在跨域问题**，只需在小程序后台配「request 合法域名」。
现有 `dota.playerallocationsystem.online` 已是 HTTPS（Let's Encrypt），满足要求。

已确认的关键接口：

| 接口 | 小程序用途 | 备注 |
|---|---|---|
| `/api/tournaments`、`/api/tournaments/[id]` | 赛事列表 / 详情 | 直接可用 |
| `/api/tournaments/[id]/matches` | 赛程与阵容 | 返回 170 条记录，需加 `limit` 参数分页 |
| `/api/map/geo?adcode=` | 地图几何数据 | **直接可用**，含 `features[].path` |
| `/api/hero-icon/[slug]`、`/api/avatar/[id]` | 英雄头像 / 群友头像 | `<image>` 直接用，需配 downloadFile 域名 |
| `/api/support` | 反馈与错误上报 | 复用现有 `kind=error` 采集 |

### 2. 地图：能在 canvas 2d 里完整复现

实测 `public/data/cn/440300.json`：

```
viewBox: 0 0 1016 591 | 9 个区块
单区块: { name, adcode, path, center }
path: "M697.1 126.5L698 122.9L697.9 116L..."  命令只含 M / L / Z
```

**只有 `M/L/Z` 三种命令、坐标是空格分隔的数字** —— 小程序 canvas 2d 可以逐点解析成
`moveTo / lineTo / closePath`，不依赖任何第三方库，与现有「零依赖自绘 SVG」的思路一致。

- 点击命中：优先 `ctx.isPointInPath(path2d, x, y)`（基础库 2.9.0+）
- 兜底：算点击点到各区块 `center` 的最近距离
- 南海诸岛插图：同一个 canvas 内 `translate + scale` 画子图，**领土表达不能省**
- 数据来源：走 `/api/map/geo`（全国 99.8KB / 单省 30~78KB），**不打进小程序包**

### 3. 合规：企业主体的门槛比想象低

微信官方文档对「社交 > 社区/论坛」类目的资质要求（2 选 1）：

1. **《非经营性互联网信息服务备案核准》** ← 就是 **ICP 备案**，不是增值电信业务许可证
2. 《统一社会信用代码证》（机构类型：机关，政府主体适用）

所以企业主体 + **域名已 ICP 备案** 即可申请该类目，不需要办理 ICP 许可证。

但还有几件事绕不过去：

| 事项 | 周期 | 说明 |
|---|---|---|
| 企业主体认证 | 1~3 天 | 营业执照 + 对公账户打款验证，300 元/年 |
| **小程序备案** | **7~20 个工作日** | 2023 年起强制，未备案不能发布 |
| 类目申请（社交-社区/论坛） | 1~15 天 | 提交 ICP 备案截图 |
| 隐私保护指引 | 1 天 | 必须声明收集 openid、昵称头像、设备信息 |
| 内容安全机制 | 开发时做 | 接入 `security.msgSecCheck` + 举报入口 |

> ⚠ 三者主体必须完全一致：微信认证主体 = 小程序备案主体 = ICP 备案主体。
> 用别人公司资质挂靠会被「主体一致性穿透校验」拦下。

## 三、架构

```
微信小程序（新建 miniprogram/）
   │  wx.request + Authorization: Bearer <token>
   ▼
现有 Next.js 后端（不拆服务）
   │  43 个 API 复用 + 新增 3 个 /api/mp/*
   ▼
PostgreSQL（加 1 张表 + 2 个字段）
```

**核心原则：后端只有一套。** 不新建 BFF、不复制业务逻辑，避免两端数据口径漂移。

### 后端改造清单（很小）

| 改动 | 位置 | 说明 |
|---|---|---|
| token 认证 | `lib/auth.js` | `getSession()` 增加 `Authorization: Bearer` 分支，兼容现有 cookie |
| 微信登录 | 新增 `pages/api/mp/login.js` | `wx.login` 的 code → `jscode2session` → openid → 签发 token |
| 账号绑定 | 新增 `pages/api/mp/bind.js` | 未绑定的 openid 用「用户名+密码」绑到 `players.id` |
| 绑定表 | 新建 `mp_bindings` | `openid`(unique) / `unionid` / `player_id` / `created_at` |
| 内容安全 | 新增 `lib/wx-security.mjs` | `security.msgSecCheck` 包一层，反馈/报名提交前调用 |
| 分页 | `pages/api/tournaments/[id]/matches.js` | 增加 `limit/offset`，小程序不能一次拉 170 条 |

**不改的部分**：所有业务 API 的出入参保持原样，网站完全不受影响。

### 小程序端目录与分包

主包上限 2MB、总包 20MB。23.4k 行页面全部塞主包必然超限，必须分包：

```
miniprogram/
├── app.js / app.json / app.wxss      # 全局：token、主题变量、请求封装
├── pages/                            # 主包（≤2MB）
│   ├── index/                        # 首页聚合（最近赛事、我的战绩、入口）
│   ├── tournaments/list/             # 赛事列表
│   └── login/                        # 登录 / 微信绑定
├── packageTournament/                # 分包 A：赛事
│   ├── pages/detail/                 # 赛程、阵容、名次、对局外链
│   └── pages/signup/                 # 报名
├── packageMember/                    # 分包 B：群友
│   ├── pages/list/                   # 成员列表（筛选、搜索）
│   ├── pages/detail/                 # 个人主页 + 最近对局
│   └── pages/map/                    # canvas 三级地图
├── packageContent/                   # 分包 C：内容
│   ├── pages/food/                   # 美食
│   ├── pages/party/                  # 开黑房间
│   └── pages/feedback/               # 反馈
├── packageProfile/                   # 分包 D：我的
│   ├── pages/index/                  # 个人资料
│   ├── pages/my-tournaments/         # 我的赛事
│   └── pages/change-password/
└── components/                        # 复用组件：赛事卡、阵容行、地图画布
```

**不打包**：地图数据（走接口）、英雄图鉴大图（走图片接口）。

## 四、四个技术难点与方案

### 1. 样式体系：令牌能复用，布局必须重写

现有 9487 行 CSS 里：

- `styles/tokens.css`（340 行）→ **几乎原样搬**成 WXSS 变量（`page { --bg-page: #15171a; ... }`）
- `layout.css` / `shell.css` / `home.css`（7.2k 行）→ 重写。原因：大量 `display: grid`、
  复杂选择器、伪元素（`::before` 的 `·`、`::after` 的 `↗`），小程序支持度不同

**主题**：`app.json` 开 `"darkmode": true` + `useDarkMode`，监听 `wx.onThemeChange`。
默认与网站一致走日间，夜间跟随系统。品牌三档色（`--brand` / `--brand-solid` /
`--brand-on-soft`）的对比度关系必须保留 —— 这是之前踩过的坑，深色上一律实底用 `--brand-solid`。

### 2. 地图 canvas（前面已验证）

```
拉 /api/map/geo?adcode=  →  features[].path
   ↓ 解析 "M..L..Z"
moveTo/lineTo/closePath → fill(热力色) + stroke(发丝线)
   ↓ 点击
isPointInPath 命中 → adcode 下钻 → 重新拉数据重绘
```

热力分档直接复用现有 `heatScale` 阈值，保证小程序与网站的深浅一致。

### 3. 登录：不依赖 cookie

小程序 `wx.request` 不会自动管理 cookie，所以：

- 后端签发复用现有 HMAC（`sha256(AUTH_SECRET)` 派生密钥），只是从 cookie 换成 token
- 前端存 `wx.setStorageSync('token')`，请求拦截器统一加 `Authorization: Bearer`
- 首次进小程序：`wx.login()` 静默拿 openid → 未绑定则引导「用网站账号绑定」
- **不默认获取昵称头像**（`getUserProfile` 已收紧，非必要不申请，减少审核摩擦）

### 4. 数据量：必须分页

`/members` 的 SSR payload 已到 **216KB**（Next 自己都在报警）。小程序里：

- 列表按 20 条分页，滚动加载
- 对局记录默认 20 条（网站是 200 条）
- 筛选条件走 URL query，不把全量数据常驻内存

## 五、阶段规划

| 阶段 | 内容 | 产出 | 预估 |
|---|---|---|---|
| **P0 合规前置** | 企业认证、小程序备案、ICP 备案截图、类目申请、配置合法域名 | 小程序可发布状态 | 1~2 周（可与 P1 并行） |
| **P1 基座 + 只读核心** | 脚手架、请求封装、token 层、主题、赛事列表、赛事详情（赛程/阵容/名次/对局外链）、成员列表、个人主页 | **可提交审核的第一版** | 2 周 |
| **P2 地图与内容** | canvas 三级地图（含南海诸岛）、美食、开黑房间、搜索 | 功能覆盖 70% | 1.5 周 |
| **P3 账号与 UGC** | wx.login 绑定、报名、我的赛事、反馈、改密码、内容安全校验、举报入口、隐私协议页 | 与网站功能对齐 | 2 周 |
| **P4 打磨** | 分享卡片、订阅消息（开赛提醒）、性能与包体优化、真机兼容 | 上线 | 1 周 |

**为什么 P1 就先审核**：只读版不含 UGC，类目审核风险最低，能尽早跑通备案与提审流程。
等流程跑顺了再补 UGC，避免代码全写完才发现类目被卡。

**总计**：开发约 6~7 周，备案 2~4 周（并行则整体 7~8 周）。

## 六、明确不做

| 项目 | 原因 |
|---|---|
| 后台管理 `/admin`（4659 行，12 个页面） | 手机浏览器体验更好，小程序审核对管理后台不友好 |
| Excel 导入导出（`ExcelIO` / `TournamentPackageIO`） | 后台专用，需要文件选择器 |
| 战力/AI 分析（`/api/ai-analysis`） | 非高频功能，可后续按需加 |
| 网站端的 Excel 批量操作、`/diag` 诊断页 | 运维工具，不具备用户价值 |

## 七、风险

| 风险 | 影响 | 应对 |
|---|---|---|
| **类目审核不通过** | 无法上线 | P1 先按只读提交；备选类目「工具 > 信息查询」，但 UGC 功能要暂时摘掉 |
| **内容审核机制不足** | 上线后被举报下架 | 反馈/报名文本全部过 `msgSecCheck`，提供举报入口，保留人工复核 |
| 两套前端维护成本 | 改接口要验两端 | 小程序只调 API，不复制业务逻辑；关键接口保持向后兼容 |
| canvas 兼容性 | 低版本安卓机地图异常 | 基础库设 `>=2.9.0`，命中检测做 `isPointInPath` + `center` 双兜底 |
| 包体超限 | 提交失败 | 严格分包，地图与图片全走接口 |
| 数据口径漂移 | 两端数字不一致 | 筛选/统计复用 `lib/` 里的纯函数（`hero-filters.mjs`、`match-format.mjs`） |

## 八、第一步该做什么

如果按这个规划走，P0 和 P1 可以并行。建议先启动这三件事：

1. **确认域名 ICP 备案主体**是否能对上企业营业执照（不对的话类目会被驳回，要先处理）
2. 注册/认证小程序，拿 **AppID**（后续 `project.config.json` 要用）
3. 我这边先搭 P1 的基座：脚手架、请求层、token 改造、赛事列表与详情

后端改动很小，可以在不破坏网站的前提下先做，网站和小程序共用一个服务。
