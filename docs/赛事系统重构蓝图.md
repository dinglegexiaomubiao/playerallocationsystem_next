# 群英荟 · 管理后台与赛事系统 重构蓝图

> 状态：P0 数据模型已定稿，待确认后进入编码。
> 最后更新：2026-10-20
> 关联背景：本项目由「Dota2 选手分配工具」演进为「专业 Dota2 社区网站」，已有四大板块（首页/赛事/群友/美食）+ 服务端鉴权（HMAC cookie 会话 + 按破坏性分层）。

---

## 1. 目标总览

把现有「孤立的管理后台（/main 分配工具）」升级为完整的赛事管理系统，打通四条数据链：

```
账号（play_score） ──1:1── 选手（players） ──报名──▶ 赛事（tournaments）
                                                    │
                        队伍（teams） ──组队──▶ 报名/参赛（participations）
                                                    │
                        赛程/对阵（matches） ◀──由赛事编排
```

核心新增能力：
1. 群友自助注册（填写完整选手资料），自动写入群友信息。
2. 管理员管理赛事（赛季 CRUD + 7 态状态机 + 赞助奖金）。
3. 群友报名比赛（自动通过）→ 管理员手选队长 → 队长建队拉人。
4. 比赛流程与结果（对阵编排、比分录入、晋级、名次）。
5. 趣味机制「仇人」（单向标注，组队/对战有联动展示）。

## 3. 数据模型（P0 定稿）

### 3.1 改造现有表

#### `players`（全局，只存「跨赛事不变」的部分）

| 列 | 类型 | 说明 |
|---|---|---|
| `region` | varchar(50) | 默认地区（新增，可被赛事快照覆盖） |
| `self_intro` | text | 默认自我评价（新增，可被赛事快照覆盖） |
| `enemies` | text | 默认仇人 player_id 列表（新增，可被赛事快照覆盖） |

> **关键设计**：`players` 里的这些字段只是「默认值」。选手报名某赛事时，会生成一份**赛事内快照**（见 `tournament_players`），此后该赛事里的资料以快照为准，可独立修改而不影响其它赛事。
> `steamid`（`game_id`）是唯一跨赛事不变的字段。

#### `play_score`（打通账号 ↔ 选手）

| 列 | 类型 | 说明 |
|---|---|---|
| `player_id` | bigint | 关联 `players.id`，注册时回填（新增，可空，兼容旧账号） |

#### `tournament_players`（**新建 · 赛事选手快照**）

> 这是本重构最核心的新表。解决两个硬约束：
> 1. 一个群友可报名多个比赛，每个比赛里的分数/位置/英雄/地区/评价/仇人都可能不同。
> 2. 队长身份要限定在「赛事 × 选手」维度，不能跨赛事串味。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | serial | 主键 |
| `player_id` | bigint | 全局选手 id（steamid 在这） |
| `tournament_id` | int8 | 所属赛事 |
| `score` | int | 赛事内分数 |
| `positions` | text | 赛事内位置（逗号分隔） |
| `heroes` | text | 赛事内英雄 |
| `region` | varchar(50) | 赛事内地区 |
| `self_intro` | text | 赛事内自我评价 |
| `enemies` | text | 赛事内仇人 |
| `signup_status` | varchar(20) | `approved`/`withdrawn`（自动通过默认 approved） |
| `is_captain` | boolean | **赛事内队长**（管理员手选；天然限定在本赛季） |
| `signed_at` | timestamp | 报名时间 |

> 唯一约束：`(player_id, tournament_id)` 唯一，一个选手在一个赛事里只有一条快照。

#### `tournaments`（状态机 + 结果）

| 列 | 类型 | 说明 |
|---|---|---|
| `status` | varchar(20) | 7 态之一，见 §3.3（原有，但取值规范化） |

> 现有 `champion_team_id` / `runner_up_team_id` / `third_place_team_id` 保留，作为「最终结果」的落点。

### 3.2 新建表

#### `tournament_rounds`（比赛轮次/阶段）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | serial | 主键 |
| `tournament_id` | int8 | 所属赛事 |
| `name` | varchar(50) | 阶段名（淘汰赛/半决赛/决赛…） |
| `order_no` | int | 阶段顺序 |
| `created_at` | timestamp | |

#### `matches`（对阵/赛程）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | serial | 主键 |
| `tournament_id` | int8 | 所属赛事 |
| `round_id` | int | 所属轮次 |
| `team_a_id` | int | A 队 |
| `team_b_id` | int | B 队 |
| `team_a_score` | int | A 队比分 |
| `team_b_score` | int | B 队比分 |
| `winner_team_id` | int | 胜者（可空，未出结果时） |
| `status` | varchar(20) | `scheduled`/`ongoing`/`finished` |
| `order_no` | int | 场次顺序 |
| `note` | varchar(200) | 备注 |

#### `teams` 增强

| 列 | 类型 | 说明 |
|---|---|---|
| `captain_id` | bigint | 队长 player_id（新增）；队伍由管理员选队长时**自动生成** |

> **建队规则（D8 已定）**：管理员在赛事里选定队长后，系统**自动为该队长生成队伍**（`teams` 插入一条，`captain_id` 指向该选手）。队长不自己建队。
> 队伍成员通过 `tournament_players.team_id`（或复用 `team_players` 关联）挂入，见 §5。

### 3.3 赛事状态机（7 态，管理员手动切换）

```
筹办中 (planning)
   │
   ▼
进行中 (ongoing) ──延期──▶ 延期 (postponed) ──▶ 进行中 (ongoing)
   │
   ▼
淘汰赛 (elimination) ──▶ 半决赛 (semifinal) ──▶ 决赛 (final)
                                                     │
                                                     ▼
                                                已完赛 (finished)
```

| 状态 | 英文枚举 | 徽标色 |
|---|---|---|
| 筹办中 | `planning` | 灰 |
| 进行中 | `ongoing` | 蓝 |
| 淘汰赛 | `elimination` | 青 |
| 半决赛 | `semifinal` | 紫 |
| 决赛 | `final` | 红 |
| 已完赛 | `finished` | 绿 |
| 延期 | `postponed` | 琥珀 |

> 现有数据全部是 `planned`，需要一次性映射为 `planning`（或保留 `planned` 作为别名）。
> 建议：新增 `planning`，同时把历史 `planned` 在读取时兼容映射为 `planning`。

## 6. 「仇人」机制细则

### 填写
- 在「编辑个人资料」中，用搜索框（昵称/steamid 模糊搜索）选中添加。
- 旁边注明：「仇人仅作趣味展示，无实际影响」。
- 与「默契队友」并列展示。

### 展示（三处 + 对战）
1. 本人资料页：`我的仇人：xxx、yyy`（与「默契队友」同级并列）
2. 对方资料页：`被 xxx 视为仇人`（**公开可见**，与默契队友同级）
3. 队伍卡片：队内存在仇人关系时，显示 `xxx 和 yyy 为仇人`
4. 对战流程图：两队对阵，若双方存在仇人关系，该场标记 `恩怨局`

### 判定规则
- 仇人是**单向**的（A→B），但「恩怨局」「队伍卡片」展示时**任意方向命中即触发**（A 恨 B 或 B 恨 A 都算恩怨）。
- 「被标记」反向查询：扫描所有 `tournament_players.enemies`（或全局 `players.enemies`）是否含当前 player_id。
- 仇人字段在「赛事快照」上，因此**同一对人在不同赛事可以有不同仇人关系**（本次报名 A 恨 B，下次报名可能删了）。

## 8. 风险与注意事项

1. **`PUT /api/foods` 全量覆盖坑**（已踩过）：新写的 PUT 接口务必明确是「全量」还是「部分」，并在文档/代码注释里写死。
2. **旧数据不绑账号**：66 选手、18 队伍、5 赛事暂不强制迁移，但要保证旧数据在新页面上仍能正常展示（`player_id` 可空）。
3. **状态枚举兼容**：历史 `planned` 要平滑映射到新枚举，避免旧赛事页面报错。
4. **队长身份失效**：队长退赛/被换后，`teams.captain_id` 与 `tournament_players.is_captain` 要同步维护，避免「孤儿队长」。
5. **仇人反向查询性能**：`enemies` 用逗号分隔字符串存，反查需全表扫描；当前 66 人规模无压力，未来量大再考虑关系表。
6. **快照与全局资料同步策略**：报名时以全局资料生成快照后，全局资料后续再改**不影响已生成的快照**（这正是「赛事内资料独立」的本意）。需要在 UI 上让用户清楚「我改的是全局默认，还是某个赛事里的资料」。
7. **队长管理范围校验**：队内写操作必须同时校验「操作者是该队伍的 `captain_id`」**且**「该队伍属于他当队长的那个赛事」，缺一不可，否则队长可跨赛事越权。
8. **自动建队幂等**：管理员重复点「指定队长」时，不能重复生成队伍；需按 `(tournament_id, captain_id)` 去重。
